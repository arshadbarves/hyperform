Updates a task of this chat's work plan: its status, fields, dependencies or criteria. Only the fields you send change.

- `status`: `in_progress` starts the task (it must be ready: its dependencies done and the plan approved); `completed` finishes it; `pending` puts it back; `blocked` and `failed` need a `reason`; `deleted` cancels it. Work on one task at a time and start it before you work on it.
- A task is completed only when every acceptance criterion holds: check criteria need a passing Verify run of their kind on the current code (run Verify after your last edit), `inspection` criteria need you to confirm them with `metCriteria`, and `user` criteria need the user. Subtasks must be closed and dependencies done. When completion is refused, the result names each criterion that does not hold yet and why; fix that and try again.
- `result` is a one-line summary of what the task produced; its dependents see it. Set it when you complete the task.
- `report` is a helper's result for the task it was dispatched for: a `summary` of what was done, plus `filesChanged`, `symbolsChanged`, `discoveries`, `decisions`, `experiments`, `testsRun`, `blockers`, `followUps`, `risks` and a `confidence` of `low`, `medium` or `high`. Send it once, before your run ends; a later one replaces it. The engine records it when the run ends, with the files your change touched and the checks you ran as it observed them; your own lists of those are kept as claims. A helper that ends without a report leaves its task blocked.
- A task whose helper was stopped before it finished (the plan paused, the task held, the chat closed or the app restarted) is back to `pending` with a resume pointer: dispatch it again with Agent `task_id` plus `resume` set to the helper the pointer names to continue in its kept worktree, or with `task_id` alone to start afresh.
- `addBlockedBy` / `removeBlockedBy` change the tasks it waits for; `addBlocks` makes other tasks wait for this one.
- `subject`, `description`, `activeForm`, `scope`, `acceptance` (replaces the criteria), `kind` and `priority` edit the task.
- Changes to requirements, invariants or tasks the user set may need the user; the result says so.
- Once this turn has read web content (WebFetch, WebSearch, or the report of a helper that did), you can still report progress (`status`, `result`, `activeForm`, `metCriteria`), but changes to what the plan says (`subject`, `description`, `scope`, criteria, dependencies, `deleted`) are refused, except on tasks proposed from web content that still wait for the user. Tell the user what you would change instead; they can do it in the Plan tab.
